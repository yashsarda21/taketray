## Phase 11 (polish and release)

- **ShareActivity's library uri points at a file that no longer declares `shareMain`** (Phase 9B release fix review, D-163 item 12). `ShareActivity.getDartEntrypointLibraryUri()` returns `package:taketray/share_main.dart`, which now holds `runShareScreen`; `shareMain` is declared in `main.dart`. Flutter 3.47.7 drops the uri (FlutterEngineGroup looks the name up in the root library), so nothing breaks today; a Flutter that honours the uri would fail with "Could not resolve main entrypoint function". Fix: point the uri at `package:taketray/main.dart` (and `ShareActivityTest`), then prove a release share on the phone. Also update two stale comments that still say `main.dart` re-exports `shareMain`: `ShareActivity.kt` line 28 and `app/patrol_test/share_test.dart` line 90. Check after every Flutter upgrade that a release share still opens the sheet.

- **A backup save that fails while writing leaves its document behind** (D-147). `saveDocument` creates the document first, then writes it; a write that fails (the storage full, the provider gone) answers an error, and the user sees "Couldn't save the backup.", but the empty or partial file stays where they chose to save it. Importing it later is refused as not a TakeTray backup, so no data is at risk. Fix idea: on a failed write, `DocumentsContract.deleteDocument` the new document, best effort.
- **Name an SD card and a USB drive apart in Add videos** (D-114). A volume's name cannot tell them apart, so every volume but the phone's is "Other storage" (numbered when there are two). Android's `StorageVolume.getDescription` would give "SD card" or the drive's name, for one more bridge call. Only seen when two folders with one name are on two storages.
- **Add videos' grid pages by offset** (D-114). A video deleted from the folder between two page reads can be skipped until the next resume (a new one is kept once, not twice). Keyset paging (after the last date and id shown) would close it, for a new bridge call. Rare: the folder must change while the user scrolls it.

- **A shade Turn off is lost when listing the volumes fails** (Phase 6 final re-review M-7). `ShadeActionReceiver` names every mounted volume for the tap; if that MediaStore call throws, the Turn off is dropped silently: Shooting mode stays on and the Still shooting? notification is gone. No clip is lost (the session continues). Fix idea: record the tap with no generations and let the capped end treat every volume as "at the tap", or keep the notification so the user can tap again.
- **A clip trashed in a gallery and restored does not come back (M-6).** The queries leave out `IS_TRASHED` rows, so the verifier takes a trashed video for gone and removes an inbox-only clip. Restoring it does not give the row a newer generation, so the scan never adds it again. A clip in a reel recovers (the next verify un-flags it). Moved here from Phase 6 (D-108): rare, and the Phase 6 job only counts and never scans, so the background work does not make it more likely.
- **Undo plus a stuck pending row can add the videos again (M-7).** A crashed recording's pending row can hold the baseline below it for days. `undoEarlierAdd` deletes the clips, and a later scan sees the same rows again past the held baseline. Only videos shot after the stuck row are affected. Fix idea: Undo records a "do not add again" marker, or the scan skips clips that Undo removed. Moved here from Phase 6 (D-108): rare, and the Phase 6 job only counts and never scans.
- **An unfinished video at the first scan of a new volume is missed** (D-108). The first scan of a volume with no baseline never holds its baseline: it stores the captured generation. So a video that is still being recorded (pending; `videosShotSince` leaves it out) or that has no length or size yet at that scan is never added by a scan (Add earlier videos can bring it in). Holding below it is not the fix: the next scan is a plain `ScanAfter` with no date filter, and every pre-session video above the held row on the card would come in. Very rare: the camera is in front while it records, and a card is seldom first read mid-recording. The idea for the fix: remember the unfinished rows' MediaStore ids with the baseline and look them up by id (`videosByIds`) at the next scans until they finish or three hours pass.
- **What is left of the re-match cost** (D-108). The re-match reads a volume's whole video list (`allVideos`) only within 24 hours of a rebuild that left clips detached, and only when the volume's generation moved since the last match. MediaStore's generation moves with any change on the volume (a photo, an edit), so on a busy day after a rebuild each app open after such a change still pays one read, on the UI isolate, for up to a day. Check it on the S24 with a few thousand videos after a rebuild; if it shows, ask MediaStore for the videos added or changed since the last matched generation (with the fingerprint fields) instead of all of them. A clip re-indexed more than a day after its rebuild is not matched (it comes in as a new clip; the old one stays missing in its reel).
- **The new-clips job over-counts behind a held baseline** (D-104). While a pending or zero-length row holds a volume's stored baseline (`holdsBaseline`, D-72), the job counts every video after that baseline, including the clips the app has already scanned past the held row, so the shade can say "5 new clips" when 2 are new, until the row clears and the baseline moves. The evening reminder adds the same count to the waiting clips shot today, so it can over-count too (D-105). Accepted in Phase 6 (D-101's definition of the count; held rows are rare). The idea for the fix: Dart also mirrors the highest generation each scan saw, and the job counts only after that (for counting only; the scan still uses the held baseline).
- **The native copy mirrors the whole waiting list on every tag** (D-106, Phase 6 final review M-6). Each tag changes `pendingShotTimes`, and `BackgroundSync` then writes every waiting clip's shot time as JSON with `commit()` and re-arms both alarms and the channels. With a few thousand waiting clips that is tens of KB rewritten per tag, on the IO thread. The evening count and the evening reminder's removal need only the clips shot since the start of today, or of yesterday for a late delivery. Send only the shots after `now - 48 h` plus a margin for the zone, and say so in D-106 item 1.
- **Shooting card rows clamp to one line at 2× text.** "Add earlier vid…", "References · 4" and "3 clips… Tag now" are cut short. This was true of the on card since Phase 1/3, and is now true of the off card too (D-90). Let a row wrap to two lines at large text, or stack its trailing part, and check it with TalkBack.

## After v1 (only if users ask for it)

- **A wrapping variant of `TtSceneHeader` in `taketray_ui` (Phase 8 Task 11 review m5; the controller's ruling: move here).** The reel page's editing sections use their own `ReelEditSectionHeader`, which copies `TtSceneHeader`'s room, type, colours and 48 dp height but lets the title and subtitle wrap and puts the button in a `Wrap` (D-128 point 2), because `TtSceneHeader` keeps its subtitle to one line and its action in the row. If another screen needs the same, add a `wrapping` option to `TtSceneHeader` in `packages/taketray_ui`, regenerate its goldens on CI (`tool/pull_ci_goldens`), and have `ReelEditSectionHeader` use it. Changing the package changes goldens that only CI makes, so it is not done in a minors batch.
- **A stalled read of an original can hold Stop (Phase 8 Task 5 review m4, D-122).** `CopyJob` reads the original without a timeout and `cancel` waits for the worker, so a provider that hangs (a picker address, a slow SD card) keeps the Stop call from returning; the screen shows Stop as working and nothing else can be tapped. A watchdog would read on a second thread with a deadline per chunk (or interrupt the read), end the file as failed and let Stop through. Do it only if the S24 or a user shows a hang with a real card or picker address; the copy reads local files, so it is rare.
- **Per-call timeouts on the editors' bridge calls inside `EditSessionService`'s queue (Phase 8 final review M-1).** Every editing write runs on one serial queue, so one native call that never answers holds copy records, Done editing, the R8 hooks of every reel (tag, untag, undo, a scan's duplicate merge) and, through the scan, `MediaLifecycle._running`. None of recovery's native calls waits on anything unbounded; the real hang is `cancelCopy` / `beforeReelDelete` → `CopyEngine.cancel` joining a worker stuck in a stalled read (the item above). Fix when that shows: a timeout on each non-interactive bridge call (`PigeonCopyBridge`: `current`, `ownRowsIn`, `deletePendingIn`, `clear`; `PigeonEditorsBridge`: `deleteCopies`, `existingCopies`, `filesInCopyFolders`, `copyFolderNames`, `freeBytes`) and a longer one on `cancel`, so the body throws at that call (recovery then logs, sets `recoveryFailed` and retries on resume). Never a `.timeout` on the whole `_serial` body: Dart does not cancel it, so it would run beside later calls and break the serial guarantee. Optional: a fast path in `beforeClipsLeaveReel` outside the queue for a reel with no session (`_keep` and `_sweepLeft` already delete the copy of a clip that left the reel while a job ran).
- **Recovery matches finished files by the planned name only (Phase 8 final review M-7, D-123).** If MediaStore gave a copy another name (a clash adds " (1)"), a restart does not match its file to the item: it stays an orphan and Try again copies the clip again. Unlikely, because the names avoid every name already in the folder. The S24 run (Task 14) can show whether MediaStore ever renames them; if it does, match by the id the engine event recorded, or by the item's name ignoring a " (n)" suffix.
- **Copy right after a restart can jump to another reel's page first (Phase 8 final re-review N-1).** After a restart, before recovery has run, tapping Copy on a reel whose copy job is held jumps to the reel page a moment before the Copying stopped screen opens; wait for recovery instead. (Cause: `CopyProgressScreen._gone` reads the engine once, finds no job and leaves silently; the controller has no job yet. Nothing is stuck or lost. - **Move clips into a reel album instead of copying (owner idea, 2026-11-12, parked).** An opt-in "Move into an album" for editors: the reel's original videos move out of Camera into `Movies/<Reel>`, so an editor can add later clips from that album with no copies and no extra space, and the album is kept (it is not a copy). If users ask for it: opt-in only, with a clear warning, skip clips that are in other reels, and record the spec change first.
- **Copy in the background with a foreground service (owner's call, 2026-11-12, parked).** Phase 8 copies with the app open and the screen kept on (D-118, decision 2), so the user must stay on the copy screen. A foreground service would let the user leave the app while it copies. It needs the `FOREGROUND_SERVICE` permission plus a typed one (`dataSync` or similar), a Play Console declaration for it, a progress notification, and a decision on `WAKE_LOCK` for a copy that outlasts the screen being off. `tool/check_release_permissions` forbids `FOREGROUND_SERVICE` and `WAKE_LOCK` today, so the check changes with it. Do it only if users ask.
